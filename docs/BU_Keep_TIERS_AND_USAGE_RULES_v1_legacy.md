## 0. 服務的樣子（前提）

- 小型的 OpenAI 相容 API 服務，給少數人用。**只有一個模型**，使用者不能選。
- 伺服器實際上同時只跑得動 2–3 個簡單對話。
- 開放對象約 25 人。
- 用量一律在請求**結束後**記帳（D5）。計量單位是 token 總數（提示＋回覆），沿用 A 版的 `usage_events`。

## 1. 等級

| 等級 | 設定值 | 給誰 | 怎麼得到 |
|---|---|---|---|
| VIP III | `vip3` | 伺服器擁有者、核心成員 | 管理員指定 |
| VIP II | `vip2` | 伺服器維護團隊、本地人員 | 管理員指定 |
| VIP I | `vip1` | 需要大量 token 的親友 | 管理員指定 |
| NORMAL | `normal` | 親友 | 預設 |
| LOW | （狀態，不是設定值） | **超過「1.5 小時尖峰保護」的 NORMAL 帳號** | 系統自動，見第 4 節 |
| GUEST | `guest` | 只拿到一把公開 API key 的人（沒有帳號密碼） | 管理員在本機發 key |

LOW 不是另一種人，是 NORMAL 帳號暫時的狀態。管理員不能把帳號「設成」LOW。

## 2. 兩個用量表

每個帳號（它名下所有 key 合計）有兩個表。GUEST 以「每把 key」為單位。

### 2.1 「1.5 小時用量」：尖峰保護，會慢慢回復

用「水桶」模型（token bucket）：

- 每個帳號有一個桶，容量 `C`（token）。桶滿時可以一口氣用掉 `C`。
- 桶以固定速度 `R`（token／秒）回水，**不管有沒有在用都持續回**，滿了就停。
- 預設 `R = C ÷ 5400`，也就是從空到滿剛好 1.5 小時。
- 請求結束後，從桶裡扣掉那一筆的 token 總數。因為是事後扣，桶可以變成負的；負值最多到 `-0.25 × C`（避免欠太多永遠回不來）。
- 畫面顯示的百分比 = `max(0, 桶內量) ÷ C`。

這就是「閒置一陣子會回來一點、但不能永遠無限用」：持續用量低於 `R` 的人永遠不會被擋；持續高於 `R` 的人，桶遲早見底。

### 2.2 「每週用量」：固定重置

- 每個帳號每週有一個上限 `W`（token）。
- **每週日 04:00 重置**，時區用主機當地時間（預設；例：`Asia/Taipei`）。可設定星期、時間、時區。
- 不回復、不累積到下一週。

### 2.3 各等級的起始值

| 等級 | 1.5 小時桶 `C` | 回水 `R` | 每週 `W` | 排隊順序 | 每帳號同時上限 |
|---|---|---|---|---|---|
| VIP III | 不設 | — | 不設 | 1 | 3 |
| VIP II | 不設 | — | 不設 | 2 | 2 |
| VIP I | 240,000 | 44.4／秒 | 3,000,000 | 3 | 2 |
| NORMAL | 80,000 | 14.8／秒 | 1,000,000 | 4 | 1 |
| GUEST（每把 key） | 20,000 | 3.7／秒 | 總額 50,000，**預設不重置** | 5 | 1 |
| LOW | 沿用 NORMAL 的桶（正在回水） | 14.8／秒 | 沿用 | 6（最後） | 1 |

數字怎麼來的見第 5 節。VIP III、VIP II 是受信任的人，兩個表都不設；用量照記、照樣顯示。

## 3. 用完時會怎樣

| 等級 | 1.5 小時桶見底 | 每週用完 |
|---|---|---|
| VIP III、VIP II | 不適用 | 不適用 |
| VIP I | 排隊順序降到和 NORMAL 相同，回到 25% 以上恢復。**不會變 LOW**（提案，見決策 D26） | 變成 LOW 的待遇直到週日重置（提案，見決策 D25） |
| NORMAL | **變成 LOW**（第 4 節） | 變成 LOW 的待遇直到週日重置（提案，D25） |
| GUEST | 回 429 並告知幾秒後再試；**不降級** | 總額用完：key 失效。有設「會重置」的 key：等下次重置，不會失效 |

## 4. NORMAL ↔ LOW

- **變成 LOW 的條件**：某一筆請求結算後，1.5 小時桶 ≤ 0。
- **LOW 的待遇**（`low_mode`，預設 `wait`）：
  - `wait`：請求仍可送出，但排在所有人後面，只有在沒有其他人排隊時才會輪到；等超過上限就回 429 並告知預估時間。
  - `block`：直接回 429，告知幾秒後回到 NORMAL。
- **LOW 期間桶照常回水。** 若 LOW 期間有請求被服務，那筆照樣扣（所以一邊用一邊回得慢）。
- **回到 NORMAL 的條件**：桶 ≥ 25% × `C`。回去後正常排隊。
- 25% 與 0% 之間的落差是故意的：避免在邊界上來回跳。
- 以起始值計算：NORMAL 從 0 回到 25% 需要 **22.5 分鐘**（20,000 ÷ 14.8）；回到全滿需要 90 分鐘。
- 管理員可在本機控制台把某個帳號的桶手動補滿（只限本機）。

狀態只有兩個、轉換只有兩條：

```
NORMAL ──（桶 ≤ 0）──▶ LOW ──（桶 ≥ 25%）──▶ NORMAL
```

## 5. 數字的推導

### 5.1 假設（全部可換）

| 代號 | 假設 | 起始值 | 來源 |
|---|---|---|---|
| `r` | 單一對話的出字速度 | 30 token／秒 | **猜的，請實測**（第 6 節） |
| `S` | 同時跑得動的對話數 | 2.5 | 擁有者：「2–3 個簡單對話」 |
| — | 平均一筆請求 | 提示 1,500＋回覆 400＝1,900 token | 假設：帶幾輪歷史的一般聊天 |
| — | 讀提示的速度 | 出字的 10 倍 | 經驗值 |
| — | 兩句話之間使用者停頓 | 90 秒 | 假設：閱讀＋打字 |
| `u` | 目標使用率 | 70% | 留三成給尖峰與 VIP |
| `N` | 尖峰時同時在聊天的帳號數 | 12 | 見 5.3 |

### 5.2 伺服器的總產能

- 一筆請求佔用 GPU：`400 ÷ 30 + 1,500 ÷ 300 = 13.3 + 5.0 = 18.3 秒`
- 一個名額的吞吐：`1,900 ÷ 18.3 ≈ 104 token／秒`
- 整台：`G = 104 × 2.5 ≈ 260 token／秒`
- 可長期分配的：`G × u = 260 × 0.7 ≈ 182 token／秒`
- 每 1.5 小時：`182 × 5,400 ≈ 98 萬 token`

### 5.3 「25 人、每人平均 1.2 個 session」的兩種讀法

| 讀法 | 意思 | 同時開著的對話 | 對產能的要求 |
|---|---|---|---|
| (i) 同時 | 尖峰時 25 人都在線，每人開 1.2 個視窗 | 30 | 每個對話佔用率 `18.3 ÷ (18.3 + 90) = 17%`，需要 `30 × 17% = 5.1` 個名額，是產能的 2 倍，**會排隊** |
| (ii) 每天 | 每人每天用 1.2 次 | 尖峰約四成的人在線 → 12 | `12 × 17% = 2.0` 個名額，**剛好夠**（使用率 80%） |

起始值採讀法 (ii) 的 `N = 12`。若實際情況是讀法 (i)，數字不用改，只是會更常有人變成 LOW、排隊更久——這正是保護機制該發揮作用的時候。

### 5.4 NORMAL 的桶

- 公平份額：`R = 182 ÷ 12 ≈ 15 token／秒` → 取 **14.8**（讓 `C` 是整數）
- 容量：`C = R × 5,400 ≈` **80,000**（約 42 筆一般請求）

效果（以起始值計算）：

| 使用方式 | 平均用量 | 與回水 14.8 相比 | 結果 |
|---|---|---|---|
| 一般聊天，每 108 秒一句 | 17.6／秒 | 略高 | 連續聊 **8 小時**才見底，等於不會被擋 |
| 程式不停地送，佔滿一個名額 | 104／秒 | 7 倍 | **15 分鐘**見底 → LOW |
| 程式同時佔兩個名額 | 208／秒 | 14 倍 | **7 分鐘**見底 → LOW（NORMAL 同時上限是 1，實際上做不到） |

### 5.5 其他等級

- VIP I：NORMAL 的 3 倍（`C = 240,000`、`R = 44.4`）。
- GUEST：NORMAL 的四分之一（`C = 20,000`、`R = 3.7`），另有總額 50,000。
- 每週 `W`：伺服器每週可分配量，以每天實際有人用 8 小時計：`182 × 8 × 3,600 × 7 ≈ 3,700 萬`。保留三成給 VIP III／II 與訪客，剩約 2,600 萬。假設 5 個 VIP I（各 3 份）與 15 個 NORMAL（各 1 份）共 30 份，每份約 86 萬 → NORMAL 取 **1,000,000**、VIP I 取 **3,000,000**（合計 3,000 萬，超賣 15%，因為不會每個人都用滿）。
- 對照：NORMAL 每天聊 1 小時約 6.3 萬 token，一週約 44 萬，是 `W` 的 44%。

### 5.6 敏感度：實際速度與人數不同時

模擬條件：3 個名額、上面的請求大小與停頓、封閉式排隊模型，模擬 6 小時（程式在規劃者的暫存區，沒有進 repo）。

| 同時在聊的對話數 | 出字 15／秒 | 出字 30／秒 | 出字 60／秒 |
|---|---|---|---|
| 8 | 使用率 75%，平均等 7 秒 | 45%，1 秒 | 25%，0 秒 |
| 12 | 96%，31 秒 | **67%，3 秒** | 37%，0 秒 |
| 20 | 100%，122 秒 | 95%，22 秒 | 62%，2 秒 |
| 30 | 100%，245 秒 | 100%，79 秒 | 88%，8 秒 |

讀法：出字速度是最關鍵的數字。30／秒時，12 個同時對話很舒服、20 個開始吃緊、30 個平均要等一分多鐘。

把名額開到 6、但每個對話因為共用 GPU 而只剩 45% 速度時：12 個對話平均等 1 秒，20 個等 13 秒，30 個等 69 秒。**開更多名額不會增加總產能**，只是把「排隊等」換成「每個人都變慢」。

## 6. 怎麼校正

只需要量一個數字：**滿載時整台每秒處理多少 token（`G`）**。

1. 用平常的模型，同時送 3 個一般長度的對話請求，重複幾輪。
2. 從 `usage_events` 取這段時間的 token 總和，除以經過的秒數，得到 `G`。（或看後端自己報的出字速度 `r`，再用 5.2 的算式。）
3. 代入：

```
R_normal = G × 0.7 ÷ N        （N：尖峰同時在聊的帳號數，起始 12）
C_normal = R_normal × 5400
VIP I    = NORMAL × 3
GUEST    = NORMAL ÷ 4
W_normal = G × 0.7 × 每日有人用的秒數 × 7 × 0.7 ÷ 份數
```

上線兩週後，看三個實際數字再調：尖峰同時活躍帳號數（校正 `N`）、多少比例的帳號曾變成 LOW（目標：一般聊天的人 0%）、平均排隊等待（目標：尖峰 < 30 秒）。

## 7. 同時名額與排隊

### 7.1 名額

- 全域同時名額 `slots`，預設 **6**（擁有者指定），可設定。
- **警告：名額數必須配合後端真正的平行數與 context。** llama.cpp 會把總 context 平分給各平行槽位，LM Studio 的行為需實測；名額開 6 但後端每槽 context 變成六分之一時，會出現 `Context size has been exceeded`（見 `docs/plan/TODO.md` T1）。啟動檢查要比對 `slots` 與後端回報的平行數／context，不符時在本機控制台顯示警告。
- 產能提醒見 5.6：伺服器實際只跑得動 2–3 個時，開 6 個名額是讓 6 個人同時「慢慢出字」。

### 7.2 出隊規則（只有三條）

1. 等級順序：VIP III → VIP II → VIP I → NORMAL → GUEST → LOW。正在跑的不會被中斷。
2. 同一等級內按帳號輪流；同一帳號內先到先得。每個帳號受第 2.3 節的同時上限限制。
3. 保底：每放行 6 筆，至少 1 筆給「等最久的 NORMAL 或 GUEST」（若有人在等），避免 VIP 滿載時其他人完全不動。LOW 不享有保底。

### 7.3 上限

| 設定 | 預設 | 超過時 |
|---|---|---|
| 排隊總長 `max_length` | 30 | 503，附 `Retry-After` |
| 每帳號排隊數 `max_per_account` | 2 | 429，附 `Retry-After` |
| 最長等待：公開入口（不串流） | 60 秒 | 429，附 `Retry-After` 與訊息。原因：Cloudflare 約 100 秒會切斷 |
| 最長等待：本機入口 | 600 秒 | 同上 |

### 7.4 讓使用者知道自己在排隊

保持簡單，四種管道，內容相同（位置、預估秒數、等級）：

| 用戶端 | 怎麼告知 |
|---|---|
| 不串流（公開入口的預設） | 排到了就正常回覆，回應標頭帶 `X-LLMOP-Queue-Waited`（實際等了幾秒）。等超過上限則回 429：`{"error":{"code":"queue_wait","message":"目前排第 3 位，約 40 秒後再試 (queue position 3, retry in ~40s)"}}`＋`Retry-After: 40`。OpenAI SDK 會依 `Retry-After` 自動重試 |
| 串流（本機入口的預設） | 先回 SSE 標頭，排隊期間每 5 秒送一行註解 `: queue position=3 eta=40`。標準用戶端會忽略註解行，連線不會斷 |
| 加密模式 | 沿用 202＋輪詢，`pending` 回應多帶 `"queue":{"position":3,"eta":40}`；用戶端外掛把它轉成上面兩種之一 |
| 入口網頁與任何程式 | `GET /v1/me`（帶 key）回傳：等級、目前狀態（NORMAL／LOW）、兩個表的剩餘量與下次重置時間、目前排隊位置與預估等待 |

預估等待 = 前面排隊數 × 最近 20 筆的平均耗時 ÷ 名額數。

### 7.5 串流預設

公開入口（trycloudflare）預設**不串流**；本機入口預設串流（D3 已定）。

## 8. GUEST 與臨時 key

- GUEST key 不屬於任何帳號，只能由管理員在本機控制台發。
- 欄位：標籤、總額（預設 50,000）、到期日（可空）、是否加密、**是否重置**（預設否）。
- **不重置（預設）**：總額用完或到期，key 失效，之後一律回 401 `key_exhausted`／`key_expired`。**唯讀儀表板連結仍然看得到這把 key**，顯示「已用完」或「已到期」與日期，讓對方知道原因。
- **會重置**：總額在每週日重置；用完時回 429 並告知重置時間；**這種 key 不會因為用完而失效**（仍可因到期或被撤銷而失效）。
- GUEST 永遠不會變成 LOW，也不會升級。1.5 小時桶見底時回 429 等回水。

## 9. 設定檔（`config.yaml`）

```yaml
usage:
  window_seconds: 5400          # 1.5 小時桶：從空到滿的時間
  recover_at: 0.25              # LOW 回到 NORMAL 的門檻
  debt_floor: 0.25              # 桶最多可欠 25%
  low_mode: wait                # wait | block
  week_reset: { weekday: sun, time: "04:00", timezone: local }   # local 或 Asia/Taipei 之類

tiers:
  vip3:   { priority: 1, max_concurrent: 3 }                       # 不寫 bucket / weekly = 不設限
  vip2:   { priority: 2, max_concurrent: 2 }
  vip1:   { priority: 3, max_concurrent: 2, bucket: 240000, weekly: 3000000, on_bucket_empty: as_normal }
  normal: { priority: 4, max_concurrent: 1, bucket: 80000,  weekly: 1000000 }
  guest:  { priority: 5, max_concurrent: 1, bucket: 20000,  budget: 50000, reset: false }

queue:
  slots: 6                      # 必須配合後端的平行數與 context（見 7.1）
  max_length: 30
  max_per_account: 2
  max_wait_seconds: { public: 60, local: 600 }
  fair_share_every: 6           # 每 6 筆至少 1 筆給等最久的 NORMAL／GUEST

accounts:
  alice: { tier: normal }
  bob:   { tier: vip1, bucket: 300000 }     # 個別帳號可覆寫任何一項
```

A 版原有的 `default_quota`（每日／每月 token、每分鐘請求數）在合併後由本文件的兩個表取代；`requests_per_minute` 保留為防呆上限。

## 11. 邊界情況

| 情況 | 處理 |
|---|---|
| 一筆很大的請求把桶扣成負的 | 允許，最多欠 25%；之後照常回水 |
| 請求在排隊時帳號變成 LOW | 已在排隊的那筆移到 LOW 的順位 |
| 請求在排隊時使用者斷線 | 立刻離隊，不佔名額、不記用量 |
| 請求失敗或中途取消 | 已產生的 token 照記、照扣 |
| 後端沒回報用量 | 用字數估算（A 版現有作法），照扣 |
| 管理員改了某帳號的等級 | 立刻生效；桶按比例換算到新容量 |
| 程式重啟 | 桶的水位與上次更新時間存資料庫；重啟後依經過時間補水 |
| 主機時鐘被往回調 | 回水量以不小於 0 計；每週重置以「上次重置時間」為準，不重複重置 |
| 週日重置時有請求正在跑 | 那筆結算時記在新的一週 |
| 同一帳號多把 key | 兩個表合計；每把 key 的用量仍分開顯示 |
| VIP III／II | 不擋、不降級，只受同時上限與排隊順序影響 |
