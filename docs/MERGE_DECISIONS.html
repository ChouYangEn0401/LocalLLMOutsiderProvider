一、現在是怎麼運作的

看得到對話明文的範圍只有密文經過

(a) 一筆聊天請求從頭到尾

A 的重點

  • 驗證、額度、轉送、記帳都在同一個程式裡。
  • 真的串流：後端每吐一段，閘道就轉一段；中途取消也會結算用量。
  • 每筆請求在資料庫記一列：誰、哪把 key、模型、token 數、耗時、成功與否。不記對話內容。

B 的重點

  • 閘道能做的只有：認 key、驗簽章、算額度、挑一台有這個模型的 worker、轉送。
  • 沒有串流：worker 收到串流請求會拒絕；用戶端代理等整段算完再假裝成串流送給應用程式。
  • 等太久不會斷：閘道先等 80 秒，還沒好就請用戶端改用輪詢，避開 Cloudflare 的 100 秒限制。
  • 紀錄只有代號、模型、大小、狀態；有測試禁止把內容寫進紀錄。

(b) 登入 → 拿 key → 使用

A：使用者自助

  1. 你在 config.yaml 開帳號（或用 llmop add-user）。
  2. 朋友開網頁用帳號密碼登入，拿到 12 小時有效的登入狀態（cookie；資料庫只存它的雜湊）。
  3. 他按「申請新金鑰」，sk-llop-… 只顯示這一次；資料庫只存雜湊。
  4. 他在程式裡填網址與 key。API 只認 key，網頁只認登入狀態，兩者不互通。
出處：web/routes.py:467, 613、auth.py:96, 114、security.py

B：管理員發放

  1. 使用者在自己電腦執行 llmop client keygen，產生簽章鑰匙，把公開的那半傳給你。
  2. 你在閘道那台機器開管理頁（預設只接受本機連線），建立 API key 並綁上他的公鑰。
  3. 你把 llmop_sk_… 傳給他；他另外要從 worker 的畫面抄下 worker 公鑰來「釘選」。
  4. 他啟動本機代理，應用程式指向 127.0.0.1:8788。
出處：gateway/admin.py:254, 316、client/config.py、docs/DEPLOY.md §5–6

(c) 額度怎麼算

A：事後記帳（軟性）

  • 以帳號為單位：每日／每月 token、每分鐘／每日請求數、同時請求數、單次上限。
  • 放行前只看「目前已記的用量超過了沒」；算完才把這筆記進去，所以單筆可能略超。
  • 每日額度在主機當地時間午夜重置。
出處：quota.py:119-180、store.py:268

B：先預扣再結算（硬性）

  • 以每把 key為單位：每日請求數、每日 token。
  • 放行前先把這筆的 max_tokens 預留起來，回來再換成實際用量。
  • 以 UTC 換日。用量數字由 worker 明文回報給閘道。
出處：gateway/store.py:257-310、gateway/worker_ws.py:116

D5 已決定合併後一律採 A 的事後記帳，搶資源的問題改用佇列處理。

(d) 怎麼讓外面連得進來

A

閘道只聽 127.0.0.1:8780。llmop 自己啟動並看管 cloudflared：它從你家連出去到 Cloudflare，拿到一個 https://xxx.trycloudflare.com 網址（每次重啟都換；也支援固定網域）。路由器不用開 port，Ollama 的 11434 永遠不對外。

出處：tunnel.py:142、config.example.yaml

B

閘道同樣只聽本機並靠 cloudflared 對外（要自己手動啟動）。多了一段：worker 主動連出一條 WebSocket 到閘道，並每 25 秒互相確認還活著。所以 LLM 那台機器沒有任何對內的入口，放在防火牆後面也能用。

出處：worker/link.py:63-120、gateway/worker_ws.py:32

(e) B 的端對端加密，白話版

機制白話防的是什麼
釘選 worker 公鑰使用者把 worker 畫面上顯示的那串公鑰抄進自己的設定。之後只把內容鎖給這把鑰匙。一定要從 worker 的畫面抄，不能相信閘道給的。閘道被入侵後換上自己的鑰匙來偷看
簽章每筆請求用使用者自己的私鑰蓋章。閘道驗一次，worker 不信閘道、自己再驗一次。只偷到 API key 的人（例如從 Cloudflare 那一段）冒用額度
加密請求內容用 worker 的公鑰鎖起來，只有 worker 的私鑰打得開。內容補到 1 KiB 的倍數，讓人看不出確切長度。閘道、Cloudflare、路上任何人讀到對話
加密回覆使用者每筆請求都附一把只用一次的鑰匙（藏在密文裡）。worker 用它鎖回覆，所以只有發問的人打得開。閘道把 A 的回覆調包給 B
防重放請求帶時間，前後差超過 5 分鐘就拒絕；worker 記住看過的請求編號，同一筆不收第二次；worker 重開機前的請求一律作廢。有人把攔到的請求重送一次來消耗 GPU
可選：worker 也釘選使用者worker 設定裡列出允許的使用者公鑰。閘道被入侵後拿別人的鑰匙來佔用你的 GPU
出處：crypto.py、worker/replay.py:20-45、client/sdk.py:184、docs/SECURITY.md §3–8

B 自己列出的極限：LLM 那台機器本身看得到一切；閘道看得到誰在什麼時候用哪個模型、用了多少；請求沒有前向保密（見 D6）。

D1

一個閘道能不能同時開「直連」和「加密」？

待決

閘道有兩種收件方式。直連：收一般的 OpenAI 請求，閘道看得到內容，任何現成工具都能用。加密：只收鎖好的信封，閘道看不到內容，使用者要先裝 llmop client。兩者現在用同一個網址路徑，所以要嘛擇一，要嘛把加密的搬到另一個路徑 /e2e/v1/。

例子你把網址給兩種人。朋友小明只想用現成的聊天 App，填網址和 key 就好（直連）。你自己在公司用 SYNOX 問跟工作有關的事，不想讓 Cloudflare 看到（加密）。選 B，兩個人用同一個網址、同一台閘道；選 A，你得決定這台閘道只服務哪一種，另一種人連不上（或你要架兩台）。
選項做法好處壞處
A 擇一啟動時由方案決定只開一種最單純；「這台閘道看不到內容」這句話永遠成立兩種使用者不能共用一台；要兩種就得跑兩個閘道
B 同時開直連走 /v1，加密走 /e2e/v1，可各自開關一台服務兩種人；仍然可以設成只開一種同時開的時候，走直連的那些對話閘道與 Cloudflare 看得到，容易誤以為「全部都加密」；要在畫面上標清楚每把 key 走哪一邊

使用者看到的差別只有一處：加密的使用者把程式指向自己電腦上的代理（127.0.0.1:8788），直連的使用者直接填公開網址。

選了之後的後果：選 B 要把 B 版的加密路徑改名（B 版還沒有人在用，沒有相容問題；簽章不包含路徑，安全性不變）。

規劃者建議（由你決定）B。預設方案仍然只開一種，「兩種都開」是進階選項，開的時候管理頁每把 key 旁邊標示「直連」或「加密」。
回覆範例：D1=B
D2

閘道要合成一支程式，還是兩支並存？

待決

A 的閘道和 B 的閘道是用不同工具寫的兩支程式，各有自己的帳號、資料庫、管理頁。問題是合併後要不要把它們真的併成一支。

A：合成一支
一個閘道程式一套帳號一個資料庫一個網頁
B：兩支並存
A 的閘道（直連方案時啟動）B 的閘道（加密方案時啟動）兩套帳號兩個資料庫兩個網頁
選項做法好處壞處
A 合成一支把 B 閘道約 1,500 行移到 A 的程式裡帳號、額度、佇列、設定區只有一套；D1 的「同時開」才做得到；你要的完整控制台才做得到要重寫 B 閘道的測試（約 900 行）與端到端測試工具（約 660 行）；工期最長的一項
B 兩支並存原樣保留，依方案啟動其中一支最快，幾乎不用改 B；B 的 563 個測試原封不動朋友的帳號在兩邊各建一次；VIP 與佇列要做兩遍；設定區只能是「連到另一個頁面」；D1 只能選 A
規劃者建議（由你決定）A。你提的需求（完整設定區、VIP、佇列、唯讀外網）都假設只有一套帳號與一個閘道。
回覆範例：D2=A
D3

加密模式要不要做真的串流（邊算邊出字）？

待決

B 版現在不支援串流：worker 算完整段才送回，使用者看到的是等很久、然後整段一次跳出來。SYNOX 一律用串流模式，所以現在也是整段跳出來。

選項做法好處壞處
A 做，預設開每 150 毫秒把新出的字加密成一小段送出；使用者可逐筆關掉打字機效果；長回答不必乾等；中途取消可以省 GPU閘道與 Cloudflare 會知道回覆大概多長、出字多快（內容仍看不到）；多一個階段的工作量
B 不做維持現狀洩漏最少（只知道總大小）；不用多做體驗差；SYNOX 每次都要等整段
C 做，預設關功能有，但使用者要自己打開預設最保守多數人不會去開，等於白做
規劃者建議（由你決定）A，並提供 worker 端的總開關（在意洩漏的人可以整台關掉）。
回覆範例：D3=A
D4

管理與設定頁從外網能做什麼？

已決定

你已決定：從外網連進來只能看，不能改。所有寫入與操作（改設定、帳號、額度、等級、發 worker 註冊碼、輪替金鑰、重啟…）只能在本機做。

「不能改」的做法不是把按鈕變灰，而是那些會改東西的網址在外網那一面根本不存在。外網看到的管理頁還會遮掉後端的內部網址、設定檔路徑與所有秘密。

額度怎麼算、大家搶 GPU 怎麼辦？

已決定

你已決定：用量在請求結束後才記帳；不靠「先扣額度」來擋人，改用排隊；另外有不受額度限制、而且優先的 VIP。

情況系統怎麼回應
排隊總數滿了（預設 32）回 503，附「幾秒後再試」
同一個人排太多（預設 4）回 429，附「幾秒後再試」

使用者在排隊時斷線立刻離隊，不佔名額、不記用量

等級寫在 config.yaml 每個帳號的 tier，也可以在本機控制台的「帳號與額度」頁用下拉選單改。

D6

「前向保密」這一版要不要做？

待決

現在的加密有一個已知弱點：請求是用 worker 的長期鑰匙鎖的。如果有人今天把密文全部錄下來，一年後又偷到那把鑰匙，就能回頭解開今天的請求。修法是讓 worker 每隔一段時間換一把短期鑰匙，舊的丟掉，錄下來的密文就永遠解不開。

今天
攻擊者錄下密文
一年後
偷到 worker 私鑰
結果
現在：解得開舊請求做了之後：解不開
選項做法好處壞處
A 這版不做手動定期換鑰匙並刪掉舊的（指令已有）；控制台加提醒不增加工期；風險有緩解辦法要靠人記得換；換了之後每個使用者都要更新釘選的公鑰
B 這版就做協定再加一層自動換鑰自動、不必通知使用者約多一個階段；協定更複雜，要再審一次安全設計
規劃者建議（由你決定）A。這個攻擊需要「長期錄密文」加上「日後入侵你家的機器」，先把合併做完比較實際。
回覆範例：D6=A
D7

加密用的 API key 由誰發？

待決

你問「兩個選項真的有差嗎？」老實說：安全上差別很小，主要差在方不方便。

加密用的 key 要搭配一把「簽章公鑰」（使用者在自己電腦產生一對鑰匙，公開的那半登記到閘道，私密的那半留在他電腦上，用來證明請求是他本人送的）。差別只在誰把公鑰登記上去。

A：使用者自己登記
使用者登入網頁貼上自己的公鑰拿到 key
B：只有管理員發
使用者把公鑰傳給你你在本機控制台建立把 key 傳回去
選項做法好處壞處
A 自己登記（管理員也能代發）使用者登入後自己申請，受每人 key 數量上限限制朋友不用找你；換電腦自己處理朋友的密碼被盜時，盜用者可以登記自己的公鑰來用他的額度（但只限他的額度；看不到他以前的對話）
B 只有管理員發每把 key 都由你在本機建立帳號被盜也拿不到加密 key；你清楚每一把是給誰的每次都要人工來回傳公鑰與 key；你不在就沒人能處理

選「A＋管理員也能代發」完全可以，沒有額外風險。

要注意的相依：D4 已決定外網唯讀。如果 D16 選 A（外網連使用者自己的 key 都不能申請），那 D7 就只能是 B。

規劃者建議（由你決定）A＋管理員也能代發；VIP 帳號的 key 只能本機發。
回覆範例：D7=A

SYNOX 怎麼接？能不能不要另外的代理？

待決

你希望一個架構處理所有情況。我查了 SYNOX 的程式，結論分兩半：直連可以不要代理；加密一定要。

SYNOX 的後端種類會不會帶 API key會不會串流能不能直接連統一閘道
local（server 填 ollama／vllm／lmstudio／other）不會。只送 Accept 與 Content-Type 兩個標頭會，一律串流不能，閘道會回 401。除非用下面的 ② 或 ③
openai_compat會。設定裡有 base_url 與 api_key看起來不會（呼叫的是一次回整段的函式）能，這就是它的用途（SYNOX 精靈裡寫「相容端點：公司閘道；要網址與金鑰」）

④ 經過 llmop client 代理SYNOX 填 http://127.0.0.1:8788唯一能端對端加密的作法；有串流；換方案不用改 SYNOXSYNOX 那台要多跑一個 llmop 程式

做不到的事要講清楚：端對端加密的意思是「在離開你電腦之前就鎖好」。SYNOX 自己不會鎖，所以一定要有東西在 SYNOX 那台機器上替它鎖：不是代理，就是把加密程式放進 SYNOX 本身（要改 SYNOX）。沒有任何閘道端的設計可以讓一個普通的 OpenAI 用戶端變成端對端加密。
